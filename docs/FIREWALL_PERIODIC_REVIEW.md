# 기한 정책 일치와 방화벽 정기 재검토

2026-11-13 · GitHub 개발본 / 검증용 환경 전용

## 정책과 업무 규칙

- 협의·보완·최종 확인의 기한 표시는 물론 알림도 사업에 고정된 게시본의 `imminentBusinessDays`와 공휴일을 사용한다. 임박 범위 안에서 늦게 실행되거나 기한 당일에 실행되어도 알림을 만들며, 기한 ID·종류·수신자별 중복을 방지한다.
- 기관 설정 초안의 `firewallPolicy.reviewMonths`(1~60, 기본 12개월), `reviewNoticeDays`(1~90, 기본 30달력일)를 편집·비교·게시한다. 기존 게시본에 필드가 없으면 기본값을 사용한다.
- 규칙 생성 시 사업의 게시본 정책을 규칙에 복사한다. 새 게시본은 기존 사업·기존 규칙의 주기와 날짜를 다시 계산하지 않는다. 기존 DB 규칙은 기존 재검토일을 유지하고 12개월·30일을 사용한다.
- 종료일 `9999-12-31`은 상시 규칙으로 해석한다. 최초 재검토일은 시작일 + 주기이며 과거 날짜이면 경과 업무로 남는다. 임박·경과 판정은 달력일 기준이다.
- 적용 완료된 상시 규칙만 정기 재검토할 수 있다. 현재 유효하게 배정된 ICT인프라 담당자만 판단을 저장한다. 신청자·정보보안·관리자는 조회만 가능하다.
- `KEEP`(계속 유지)는 서버의 오늘(서울)부터 다음 주기를 계산한다. `CHANGE_REQUIRED`·`REVOKE_REQUIRED`는 날짜를 미루지 않고 후속 조치가 남은 처리할 일로 유지한다. 변경은 별도 신청·협의 또는 후속 재검토로 해소하고, 회수는 실제 조치 후 기존 회수 API에 기록한다.
- 모든 판단은 사유·기록자·시간·이전/다음 재검토일로 추가 보존하며 감사 이력도 남긴다. 동시 수정은 `expectedRevision`으로 차단한다. 장비 명령, 제출본 변경, 규칙 통신 값의 자동 수정은 없다.

## 알림·처리할 일·업무 인계

- 기존 기한 알림 예약(`GET/PUT /api/deadline-reminder-schedule`)에 재검토 알림을 함께 연결했다. 수동 검증은 관리자 `POST /api/deadline-reminder-runs`의 `asOf`, `securityRequestId`를 사용한다. 실행 응답의 scanned/imminent/overdue는 기존 신청 기한 집계이며 규칙 집계가 아니다.
- 재검토 알림은 규칙·예정일·판단 차수·상태·수신자별로 중복을 방지한다. 미배정/부적격이면 관리자에게 인계 필요를 알린다. 알림을 읽어도 업무는 완료되지 않는다.
- 처리할 일과 배지는 현재 규칙 상태와 현재 배정에서 계산한다. 역할 변경·비활성화 시 기존 세션과 알림 접근은 기존 권한 규칙으로 차단되며, 새 담당자에게 남은 업무가 승계된다.
- 확정 신청도 적용 대기/적용 완료 규칙이 있으면 **ICT인프라 분야만** 관리자 재배정을 허용한다. 다른 분야나 운영 규칙이 없는 종료 신청은 기존 제한을 유지한다. 신청 목록의 관리자 인계 필요 표시도 같은 범위를 포함한다.
- API: `POST /api/firewall-rules/{id}/periodic-reviews` (`decision`, `reason`, `expectedRevision`). 규칙 조회 응답에 `reviewMonths`, `reviewNoticeDays`, `reviewStatus`, `reviewHistory`를 포함한다.

## 검증 기록

- 자동 검사: 기한 게시본의 3영업일·공휴일·당일·경과, 윤년 재검토일·임박 경계, 유지·변경 필요·회수 필요·이력·회수 후 제외, 기존 권한/목록/API 계약 회귀 검사.
- 검증용 Docker(3002/8082): 합성 사업 22 / 신청 23 / 제출본 9 / 규칙 5·6. 6개월·14일 정책, 과거 날짜 2024-08-14/15/30 및 기한 기준일로 검증했다.
- API: 정책 잘못된 입력 422·충돌 409, 임박/경과 중복 방지, 역할별 저장 차단, 미입력 사유 400, 재검토 충돌 409, 계정 비활성/역할 변경 후 기존 세션 401, 이전 담당자 접근 404, 새 담당자의 알림·처리할 일 승계, 제출본 불변 확인.
- 합성 신규 계정은 검증 후 비활성화하고 신청의 ICT인프라 배정은 활성 담당자에게 인계했다. 기관 설정은 새 게시본으로 원래 값에 복원했으며 합성 사업의 고정 정책(6개월·14일)은 보존했다.
- 브라우저 검증은 사용자 요청에 따라 보류. 공공 GitLab과 기존 제출 환경, 실제 장비는 변경하지 않았다.
