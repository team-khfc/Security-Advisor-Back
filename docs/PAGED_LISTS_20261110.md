# 신청·이력 페이지 조회 검증

2026-11-10 · Back #9 / Front #44

## 변경과 계약

신청 목록의 권한·검색·필터·정렬·건수 계산과 페이지 자르기를 DB에서 처리한다. 첫 100건 이후의 신청도 검색할 수 있고, 신청별 추가 HTTP 조회 없이 목록 요약을 표시한다. 사업별 관련 신청은 businessCaseId로 범위를 제한한다. 문서함·보완 요청·통신 정보도 동일한 서버 페이지 계약을 사용한다.

`GET /api/security-requests`는 기존 content/page/size/totalElements에 summary를 추가하고 각 항목에 createdAt/overview를 제공한다. query, businessCaseId, from/to, inbox, documentKind, supplementState와 허용 목록의 sort를 지원한다. 크기는 1~100, 페이지는 0부터 시작한다. summary는 업무함 선택 전 같은 검색·권한 조건의 전체 건수다.

`GET /api/audit-events`는 관리자뿐 아니라 신청자·담당자에게도 허용된 범위의 페이지를 제공한다. targetType/targetId/action/query/throughId를 받는다. 최초 응답의 throughId를 후속 페이지에 전달하면 새 기록 추가로 페이지가 밀리지 않는다. 같은 시각은 고유 ID로 정렬한다. 기존 신청별 배열 API는 호환 목적으로 유지하며 같은 권한 조건을 적용한다.

신청자는 본인 사업의 업무 이력만, 담당자는 활성 배정된 신청 및 해당 사업의 이력만 조회한다. 로그인·문서 다운로드·비공개 자료 조회·LLM 호출 메타는 신청자에게 숨긴다. 관리자만 전체를 조회한다. 권한은 내용과 totalElements 모두에 적용한다. 기존 403 및 보안 메타 노출을 기대하던 검사는 이 의도된 계약에 맞춰 본인 업무 이력 허용/보안 메타 제외/관리자 기록 유지로 변경했다.

- 새 HTTP 통합 검사: 신청 205건의 11페이지 전체 순회, 중복 없음, 뒤쪽 검색, 동일 시각 정렬, 사업 필터, 소유자·배정자·미배정자 구분, 잘못된 크기·정렬 거부.
- 이력 135건: 마지막 페이지 35건, 새 이력 추가 중 throughId 경계 유지, 역할별 건수·검색·보안 메타 필터 확인.
- Front `npm run format && npm run check`: 32개 파일, 293개 테스트 성공. 실제 연결 Docker 이미지 빌드 성공.

## 실제 Docker 검증

기존 연동 스택의 DB·업로드 볼륨을 유지하고 Front 3001 / Back 8081에 검증 브랜치를 배포했다. 일반 업무 API로 `목록검증1110` 합성 사업 110개와 신청 220개를 생성하고 ICT인프라·정보보안 담당자에게 배정했다. 별도 신청자 소유의 비공개 합성 신청 1개를 추가했다. 첫 신청에 답변 변경 140건, 전체 업무 이력 146건을 만들었다. 실제 장비와 기존 신청은 수정하지 않았다. AI 호출도 실행하지 않았다.

| 계정 | 합성 신청 검색 | 첫 합성 신청 이력 | 다른 신청자 이력 |
| --- | ---: | ---: | ---: |
| 신청자 | 220 | 146 | 0 |
| ICT인프라 담당자 | 220 | 146 | 0 |
| 정보보안 담당자 | 220 | 146 | 0 |
| 기관 관리자 | 221 | 146 | 1 |
| 다른 신청자 | 1 | 0 | 1 |

각 역할의 신청·이력을 마지막 페이지까지 HTTP로 순회하고 ID 중복·누락, 오래된 사업 검색, 사업별 관련 신청 2개, 빈 검색 결과를 확인했다. 최종 재배포 뒤 같은 검사를 다시 통과했다. 브라우저에서도 신청자/ICT인프라/정보보안/관리자의 이력 검색과 마지막 페이지, 타인의 이력 0건을 확인했다.

## 적용 순서와 범위

Back PR을 먼저 병합한 뒤 Front PR을 병합한다. 새 마이그레이션은 조회용 인덱스만 추가하며 기존 데이터를 변경하지 않는다. 기존 마이그레이션, 업무 전이, AI 생성 기능, 실제 장비 제어는 변경하지 않는다. 긴 이력의 배열 API를 쓰는 외부 구형 클라이언트는 페이지 API로 전환해야 조회량을 제한할 수 있다. 신청 목록은 실시간 업무 상태이므로 조회 사이 상태 변경 시 재조회하며, 이력의 throughId는 업무 상태 스냅샷을 뜻하지 않는다.
