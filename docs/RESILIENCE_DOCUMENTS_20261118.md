# 분석 복구·알림 재처리·운영 기록·문서 출력

2026-11-18 · GitHub 개발본 / 검증용 Docker 전용

공공 GitLab과 기존 제출 배포본에는 적용하지 않는다. 이 문서는 기존 운영·문서 안내의 해당 기능 제한을 갱신한다.

## 사용 순서

1. 신청자는 첨부 분석을 요청한 뒤 인터뷰의 분석 작업 영역에서 상태를 확인한다. 서버 재시작 후 대기 작업을 다시 실행하고, 15분 이상 중단된 실행은 최대 3회까지 복구한다. 명시적 실패는 같은 파일로 재시도할 수 있다. 자동 복구 결과도 미확정이며, 기존 답변 적용 시 revision 검사를 유지한다.
2. 문서·답변 모순 검사는 추출 원문을 20,000자 단위(500자 중첩)로 순차 검사한다. 완료한 구간은 즉시 보존하며, 자료별 검사 범위·추출 줄·PDF 쪽 정보를 표시한다. 인용문은 해당 원문에 존재해야 한다. 중간 실패 후 이미 저장된 구간은 남는다.
3. 관리자 업무 지표의 운영 상태 영역에서 과거 지표·경보·알림 전송 내역을 조회한다. 경보의 확인 처리는 해결과 다르다. 실패한 알림만 다시 처리할 수 있고 재처리 수행자와 시각은 DB에 보존한다. 재발송 시 현재 계정 활성·역할·신청 조회 권한을 다시 검사한다.
4. 기관 설정 초안에서 HWPX 출력 형식을 선택해 게시한다. 새 신청은 해당 게시본 형식을 사용한다. 기존 신청의 게시본은 유지하므로 예전 신청에 HWPX를 강제로 허용하지 않는다. 문서함의 서버 생성 문서에서 HWPX를 내려받는다. PDF·DOCX와 같은 문서 내용/출처/준비자료·검토 결과를 사용한다.

## 구현과 운영

- 분석 작업은 DB에 상태·시도 횟수를 저장한다. 30초마다 대기·만료 작업을 찾고 프로세스당 2개까지 실행한다. 잠금과 시도 번호로 중복/늦은 결과의 덮어쓰기를 차단한다. 즉시 재시작 복구가 아니라 임대 만료를 기다리는 경우가 있다.
- 알림 발송 의도는 업무와 같은 DB 트랜잭션에 기록한다. 10초마다 최대 20개를 가져오고 실패 시 대기를 늘려 최대 5회 시도한다. 작업 임대는 5분이며 고유 선점 토큰으로 오래된 결과를 무시한다. 화면 알림은 이벤트별 중복을 막는다. 외부 메일·웹훅은 상대 시스템의 멱등 처리가 없으면 전송 직후 중단 시 중복 수신 가능성이 있다.
- 1분마다 API·LLM·알림·예약 실행의 횟수/소요 시간/실패 수를 DB에 30일 보존한다. 프로세스 식별자로 재시작 시 카운터 초기화를 구분한다. 표본에 원문·키·사용자/신청별 식별자를 넣지 않는다. 경보는 구간 오류 3건 이상·25% 이상, 분석 20분 지연, 알림 최종 실패를 감지한다.
- 관리자 API: `GET /api/operation-history?page=0`, `POST /api/operation-alerts/{id}/acknowledgements`, `GET /api/notification-deliveries?page=0`, `POST /api/notification-deliveries/{id}/retries`. 모두 관리자 권한이며 변경 요청은 기존 CSRF 보호를 적용한다.
- 처리할 일은 권한·진행 단계로 DB 후보를 좁힌 뒤 200건 단위로 평가하고 요청 페이지에만 상세 정보를 만든다. 관리자 집계는 DB 그룹 집계를 사용한다. 정확한 전체 건수 계산에는 활성 후보 평가가 남으므로 무제한 규모를 보장하는 구조는 아니다.
- 새 마이그레이션 4개는 분석 상태/알림 대기열/운영 기록/재처리 선점·이력을 추가한다. 기존 업무 데이터 초기화나 재시드가 필요 없다. DB와 첨부 볼륨을 함께 백업한다.

## 범위와 제약

- 문서 추출 상한은 200,000자다. 일반 PDF 최대 100쪽, 스캔 PDF OCR 최대 8쪽/쪽당 제한 시간이 유지된다. 분석 요약은 첫 20,000자만 사용하며 긴 자료에는 제한 표시를 붙인다. 전체 문서 요약/자동 추출이 모두 확장된 것은 아니다. 모순 검사는 추출된 범위 내에서 확장한다.
- 추출 줄은 원본의 시각적 줄 번호와 다를 수 있다. OCR 인식 오류 및 구간을 가로지르는 의미 관계 때문에 모든 모순의 발견을 보증하지 않는다. 원문 확인과 사람의 판단이 필요하다.
- HWPX는 현재 시스템 문서 항목을 담은 기본 문단 레이아웃이다. 별도 공식 기관 서식의 고정 좌표·표 배치와 동일한 출력은 제공받은 양식에 맞춘 후속 작업이다. 구조/텍스트 왕복 검사는 수행했으나 한글 편집기 실제 렌더링은 확인하지 않았다. 구조 참고: https://github.com/hancom-io/hwpx-owpml-model
- 경보는 관리자 화면에서 확인한다. 앱 전체 정지·DB 불통 중에는 자체 감시도 멈추므로 외부 감시/알림 연계가 별도로 필요하다. Prometheus/Grafana와 외부 경보 발송은 포함하지 않았다. 운영 표본 30일, 최근 경보 목록 100건 기준이다.
- 검증 환경의 SMTP/웹훅은 꺼져 있다. 외부 실제 수신은 검증하지 않았고 채널 오류·재처리 로직을 자동 검사한다. 브라우저 실제 화면 검증은 사용자 요청에 따라 보류한다.

## 검증 기록

- 자동 검사: 분석 임대 만료/시도 상한, 알림 업무 롤백·중복·선점 만료·재처리 토큰·수행자 기록, HWPX ZIP/XML/텍스트/출처 보존, UI 재시도/경보 확인, 기존 회귀 검사.
- 검증용 API: 합성 사업 24/신청 25, 실제 AI가 20,000자 이후 개인정보 처리 모순과 인용 근거를 찾음. 병렬 분석 요청 중복 방지, 재시작 후 대기/임대 만료 작업 복구 및 미확정 결과 보존.
- 지표의 재시작 보존, 실패 경보 확인과 자동 해소, 알림 수동 재처리·중복 방지·현재 수신 권한 제외, 비관리자의 운영 API 403, 다른 신청자의 원문/문서 404.
- 합성 신청 240건 추가 후 담당자 처리할 일 252건/3페이지의 누락·중복·역할 조회와 관리자 집계를 확인했다. 해당 환경에서 전체 페이지 약 2.3초, 관리자 집계 약 0.11초였으며 운영 성능 보증 수치는 아니다.

최종 자동 검사: 백엔드 262건 중 261건 통과·기존 제외 1건·실패 0건, 프론트 396건 통과.
