# 0009. 신청·이력의 권한별 검색과 DB 페이지 조회

2026-11-10 · Back #9 / Front #44

신청 목록을 첫 100건만 받아 화면에서 필터링하면 오래된 신청·긴급 업무·관련 신청·문서가 누락된다. 전체 신청을 서버 메모리에 읽은 뒤 페이지를 자르는 방식도 데이터 증가에 비례해 자원을 사용한다.

신청 목록은 읽기 전용 JPA 네이티브 조회로 권한, 키워드, 생성일(KST), 사업 건, 서류 유형, 업무함, 문서 상태, 보완 상태를 적용하고 DB에서 정렬·LIMIT/OFFSET·건수를 계산한다. 다른 컨텍스트의 엔티티를 가져오거나 변경하지 않으며 목록용 SQL이 배정·협의·최종 확인의 표시 요약만 조합한다. 검색값은 전부 바인딩하고 정렬 SQL은 허용 목록의 상수만 선택한다. 쓰기 모델·업무 전이·도메인 메서드는 변경하지 않는다. 별도 저장형 읽기 모델이나 이벤트 소싱은 도입하지 않는다.

기존 신청 목록 필드에 createdAt, overview와 페이지의 summary를 추가한다. 기본 정렬은 화면의 생성일 최신순이며 updatedAt/id 정렬도 명시적으로 지원한다. 담당자 화면은 dueDate 오름차순을 요청한다. 모든 정렬은 고유 ID로 동률을 해소한다. summary는 같은 권한·검색·기간·문서/보완 조건에서 업무함 선택 전의 건수다. 화면은 현재 페이지 개수와 전체 건수를 구분한다.

감사 목록의 관리자 전용 제한을 F-14 도메인 정의로 교체한다. 기관 관리자는 전체, 담당자는 현재 활성 배정된 신청 및 그 사업 건, 신청자는 자기 신청/사업의 업무 이력을 본다. 신청자에게 로그인·다운로드·민감 조회·LLM 호출 보안 메타는 노출하지 않는다. 권한 제한을 검색 결과와 건수 모두에 적용한다. 기존 신청별 배열 API는 호환 목적으로 남기되 동일 권한 제한을 적용하고 새 화면은 페이지형 감사 API를 사용한다.

감사 페이지 응답의 throughId를 다음 페이지에 전달해 최초 조회 이후 추가된 기록을 제외한다. 이력은 변경·삭제되지 않으므로 동일 시각의 기록도 occurredAt+ID 정렬로 안정적으로 순회할 수 있다. ‘최신 이력 조회’ 또는 검색 조건 변경 시 기준을 해제한다. 신청 목록은 최신 상태를 읽으므로 업무 변경 후 재조회하며, 불변 이력의 기준 시점을 신청 상태의 스냅샷으로 오해하지 않는다.

계약 변경은 백엔드 PR을 먼저 병합하고 프론트 PR을 연결한다. 205건 신청과 135건 이력의 HTTP 통합 검사, 동시 이력 추가, 타인·미배정 권한, 마지막 페이지 검색, 실제 Docker 화면으로 검증한다.
