# 0011 — 현재 수신 권한으로 알림을 조회하고 처리할 일을 분리

상태: 채택 · 2026-11-10 · Back #15 / Front #48

## 문제

수신자 아이디만 확인하면 역할 변경·비활성화·재배정 뒤에도 예전 업무 알림을 읽을 수 있다. 기존 최대 100건 배열 조회는 과거 알림을 누락하며, 읽지 않은 소식과 아직 처리하지 않은 업무를 구별할 수 없다. 커밋 전 별도 트랜잭션으로 알림을 저장하면 취소된 업무도 알림으로 남는다.

## 결정

- 알림에 신청 ID와 발송 당시 수신 역할을 기록한다. 계정 활성·현재 역할·신청 소유/배정·분야 등록을 발송과 목록·건수·읽음 처리에 적용한다. 접근을 잃은 알림은 삭제하지 않고 숨긴다. 알 수 없는 링크는 발송하지 않는다.
- `GET /api/notifications`는 배열 대신 `PageResponse<NotificationResponse>`를 반환한다. `page`는 0부터, `size`는 1~100이며 기본 20이다. 권한/안 읽음 필터를 DB에서 먼저 적용하고 ID 내림차순으로 조회한다. 링크는 `/requests/{id}`다. 이는 호환 변경이므로 Back PR을 먼저 병합하고 해당 계약의 Front를 함께 배포한다. 별도 외부 클라이언트 지원이 필요한 시점에는 버전 전략을 재검토한다.
- `PATCH /api/notifications/{id}`는 현재 권한도 검사하며 반복 호출의 읽음 시각을 유지한다. PostgreSQL 정밀도에 맞춘 마이크로초 시각을 저장·반환한다.
- 재배정은 새 담당자에게, 역할/계정/분야 등록 변경으로 인계가 필요하면 활성 관리자에게 안내한다. 인계 뒤 보완 답변과 기한 안내는 현재 유효 담당자에게 전달한다.
- 업무 커밋 뒤 알림별 독립 트랜잭션에서 저장한다. 업무 롤백은 알림을 만들지 않고, 알림 저장 실패는 성공한 업무를 취소하지 않는다. 기존 수신자·이벤트 중복 방지를 유지한다.
- `GET /api/todos`와 `GET /api/todo-summary`는 동일한 현재 업무 판정을 사용한다. 알림 읽음과 업무 완료는 분리한다. 신청자는 보완·최종 검토, 담당자는 협의·보완 해소·가능한 순서의 최종 확인/확정, 관리자는 재배정을 본다. 종료 업무는 제외한다.
- 수동 기한 재실행에 선택적인 `securityRequestId`를 추가한다. 합성 검증이 다른 업무에 기한 알림을 만들지 않게 한다. 일일 전체 스케줄의 동작은 유지한다.

## 한계와 검증

알림은 커밋 이후 최선 노력 방식이며, 프로세스 중단 시 자동 재전송을 보장하는 영속 발송 대기열은 이번 범위에 포함하지 않는다. 외부 메일·메신저 실발송도 검증하지 않았다. 처리할 일은 현재 업무 객체를 모아 페이지를 나누므로 대규모 운영 시 조회 비용 측정과 DB 집계 최적화가 필요하다.

검증 결과는 [Docker 알림·처리할 일 기록](../NOTIFICATIONS_20261110.md)에 있다.
