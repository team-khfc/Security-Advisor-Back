# ADR 0006 — 지식 기반은 큐레이션 스니펫 + Postgres 전문검색(1차), 벡터 색인 미사용

- 상태: 채택 (2026-11-08)
- 관련: FUNCTIONAL_SPEC F-09, F-03, 불변 원칙 1·2·3, docs/DEVIATIONS.md #14

## 배경

명세는 공개자료 RAG 의 저장소로 PGVector 를 적었다. 그러나 1차 범위(11.11)의 코퍼스는 "팀이 항목별로 고른 공개 가이드 문장 수십 건"이고,
기관에는 임베딩 모델·색인 품질을 다룰 전문가가 없다. 의미 검색이 풀어야 할 문제(표현 불일치)가 거의 없는 규모에서 벡터 파이프라인은
비용(임베딩 공급자·재색인·평가)만 더한다.

## 결정

1. 공개 지식은 `knowledge_snippets`(출처 제목·판본·위치·적용 항목 키·적용 서류 유형·본문)에 두고, 검색은 **사람이 붙인 `field_keys` 1차 필터 +
   Postgres `tsvector`/`ts_rank`(simple 구성) 순위**로 한다. 한국어 사전이 없는 한계는 항목 키 필터가 흡수한다. 자유 질의는 접두 매칭(`:*`)으로 조사를 흡수한다.
2. 기관 비공개 컨텍스트는 문서가 아니라 구조화 레코드(`private_contexts`)로 두고 **서버가 역할로 걸러 뽑은 행만** 프롬프트의 "사실" 블록에 넣는다.
   모델은 검색하지 않는다. 신청자에게는 어떤 행도 보이지 않는다.
3. pgvector 확장·임베딩 컬럼·VectorStore 의존성은 두지 않는다. 필요해지면 같은 테이블에 `embedding` 열을 더해 RRF 하이브리드로 승격한다(검색 인터페이스 `KnowledgeSearch` 유지).
4. LLM 호출은 `LlmGateway` 인터페이스 뒤의 Spring AI 2.0(OpenAI 호환 API 하나로 상용·공개 모델 모두)으로 하고, 모델 출력의 IP·대역 토큰은 `InternalInfoGuard` 가 사실 블록과 대조해 근거 없는 내부 정보를 거른다.

## 결과

- 운영 기관의 "튜닝"은 스니펫의 항목 키를 고치는 것뿐이다. 임베딩 모델 운영이 없다.
- 심사 설명: "항목별 큐레이션 + 전문검색 RAG, 검색 계층은 교체 가능".
- 명세 F-09 의 "PGVector 색인" 문구는 개정 대상(DEVIATIONS #14).
