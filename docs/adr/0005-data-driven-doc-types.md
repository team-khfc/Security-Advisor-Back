# ADR 0005 — 서류 유형을 코드가 아니라 게시본 데이터로 정의한다

- 상태: 채택(2026-11-07, 팀장 승인 — 지침 범위 밖 작업을 의도적으로 선반영)
- 결정자: 정용석(메인 개발자) · 승인: 문성욱(팀장)
- 관련: FUNCTIONAL_SPEC.md 1장·2장(DocType), 8-1 스키마, F-06·F-08·F-15 / PROJECT_RULES.md 4장(범위) / docs/DEVIATIONS.md

## 배경

1차 범위는 서류 2종(방화벽·보안성검토)으로 고정이고, 초기 구현은 `DocType` Java enum + `security_requests.doc_type` CHECK 제약으로 유형을 코드에 박아 두었다. 그러나 확산 목표(다른 기관이 자기 설정으로 설치해 쓰는 구조)와 "서류별 차이는 필드 스키마·양식·질문 데이터로 표현"이라는 명세 원칙을 생각하면, 운영자가 새 서류(예: USB 사용 신청)를 추가할 때마다 코드 배포가 필요한 구조는 나중에 바꾸기 어렵고 비용이 크다. 그래서 동결 전에 **구조만** 데이터 기반으로 열어 둔다.

## 결정

1. 서류 유형의 목록·이름·행위 속성은 **게시본(`publications.field_schema`)의 `docTypes` 배열**이 정한다. 각 유형은 `code`(불변 식별자, `^[A-Z][A-Z0-9_]{1,29}$`)·`name`·`description`·`active`·`templateKey`(초안 양식, F-06)·`generatesFirewallRules`(확정 시 규칙 생성, F-15)·`reviewFields`(협의 분야)·`sortOrder` 를 가진다.
2. 코드에서는 `DocType` enum 을 없애고 `DocTypeCode` 값 객체(문자열)를 쓴다. 코드 분기는 유형 코드가 아니라 행위 속성(`generatesFirewallRules` 등)으로 한다.
3. DB 는 `doc_type VARCHAR(30)` 에 CHECK 제약을 두지 않는다. 유효성은 "사업 건이 고정한 게시본에 활성 상태로 있는 코드인가"를 서비스가 검사한다(없거나 비활성이면 422). 게시본 고정(불변식 8) 덕분에 유형이 나중에 비활성화돼도 진행 중인 신청은 영향이 없다.
4. 유형 코드는 한 번 게시되면 바꾸지 않는다(신청·제출본·방화벽 규칙이 코드로 참조). 이름·양식은 새 게시본 버전에서 바뀐다. 삭제는 없고 비활성화만 한다.
5. 운영자 편집·게시 화면(F-08 앞당김), 양식 템플릿의 데이터화(F-06)는 **11.11 이후** 순서로 한다. 지금 들어간 것은 1~4의 구조와 seed 게시본 v1(유형 2종)뿐이다.

## 결과

- 새 서류 추가 = 새 게시본 버전에 `docTypes` 한 줄 + 그 유형의 `fields` 추가(+ 양식). 코드 배포 없음.
- 새로운 **종류의 행위**(새 테이블·새 외부 연동)가 필요한 서류는 여전히 코드 작업이다. 데이터로 가능한 범위는 질문·양식·협의 분야·기존 행위 플래그의 조합까지다.
- 1차 범위 "서류 2종"은 seed 게시본의 내용으로 유지된다(코드가 아니라 데이터가 2종).
- API 계약: `docTypes`·`docType` 값이 enum 에서 문자열 코드로 바뀐다(값은 같음). 프론트 타입은 문자열 유니언이 아니라 `string` 으로 둔다.

## 대안

- enum 유지 + 유형 추가 시 코드 배포: 11.11까지는 가장 단순하나 확산 시 기관마다 배포가 필요해 기각.
- 별도 `doc_types` 테이블: 게시본 버전 고정과 따로 관리되어 "사업 건이 고정한 설정"의 의미가 깨진다. 게시본 JSON 안에 두는 쪽이 불변식 8과 일치해 기각.
